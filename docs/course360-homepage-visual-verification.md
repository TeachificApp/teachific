## Repeatable Monitoring Procedure

When a root screenshot appears blank, first inspect `#root` and the browser resource responses. A completed document with mounted root children and expected Course360 text indicates a capture discrepancy, even when the screenshot is blank. An empty root combined with an HTTP 429 for a Vite module indicates preview-gateway throttling; wait for the rate limit to clear and retry once with a cache-busting query parameter. Treat the issue as an application render failure only when the root remains empty after a successful JavaScript module response, and then inspect the browser console and the development-server transform logs before modifying application code.

After a subsequent clean development restart, direct local requests returned HTTP 200 for both the root and the transformed `src/App.tsx` module. The browser preview still received HTTP 429 for the same module, leaving `#root` empty. This confirms that the remaining post-restart blank preview is gateway throttling independent of the local application server; the post-restart preview verification remains open until the gateway permits an unthrottled browser module request.

After a 75-second gateway cooldown, a fresh post-restart preview navigation still displayed a blank page. This time, the browser retrieved `src/App.tsx` successfully with HTTP 200 and `text/javascript`, yet `#root` remained empty. The condition now meets the application-render investigation threshold: module delivery is healthy, but React does not mount, so the remaining work must trace the client module graph and root render path rather than treating the issue as throttling.

A direct dynamic import of the App module failed even though a same-URL browser `fetch` immediately returned the transformed App source with HTTP 200. This indicates that a transitive module request or module evaluation—not the App source endpoint itself—is preventing bootstrap. The next investigation step is to isolate the failing dependency from the App import graph before applying any application code change.

After changing the bootstrap to dynamic App loading, the restarted preview requested `src/App.tsx`, DashboardLayout, ErrorBoundary, the subdomain hook, and their initial dependencies, but the root remained empty. This shows the import begins but does not settle promptly because the broader App graph remains large. Bootstrap must render a visible shell before awaiting that graph, with a timeout-based retry option if it never resolves.

The first timeout fallback implementation still left an empty root after restart. Browser resource inspection showed only `src/main.tsx` had loaded—not its dynamic App import—and no loading shell mounted. This proves an eager dependency of `main.tsx` (the tRPC/query-provider imports or their graph) can abort before `createRoot` executes. The corrective boundary must reduce `main.tsx` to React DOM, styling, and a dynamic import of a provider-owning bootstrap module.

The immediate post-change development-preview verification was intercepted by the preview gateway before application bootstrap: the document response was `text/plain` with `Too many requests. Please try again later.` and no `#root` element. This is separate from the application bootstrap behavior and prevents a live preview verification until the gateway accepts the document request.

A single final retry after a further 75-second cooldown received the same document-level `text/plain` HTTP 429 response, again before any `#root` element or client script could load. The lightweight bootstrap behavior remains covered by source-level regression and client bundles; direct live-preview confirmation is blocked by gateway throttling rather than an observable application failure.

After the platform-root optimization, the development preview again returned an empty root and a direct LandingPage module probe received HTTP 429 with `text/plain`. The platform-root predicate and deferred loading behavior are covered by focused tests and bundles; this gateway-limited browser result does not indicate a cross-organization routing failure.
